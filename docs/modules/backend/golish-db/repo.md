# golish-db / repo

> **一句话职责**：各表的 **scoped CRUD helper**——每个表一个模块（sessions/tool_calls/findings/targets/memories/vault/…40+ 个），统一经 `scoped.rs` 做资源所有权（IDOR）校验，是全仓库 DB 读写的权威入口。

- **类型**：目录模块（属于 crate [`golish-db`](../golish-db.md)）
- **路径**：`backend/crates/golish-db/src/repo/`
- **状态**：✅ 已写卡

---

## 何时该读这张卡（给 AI 的触发提示）

- 加/改任何表的 CRUD（新 repo 方法、新表模块）时
- 任何跨服务读写——app crate 不直接写 SQL，走这里的 `repo::*`（横向耦合经 ports，纵向走 repo）
- 改 IDOR scoping 基座（`scoped.rs`）或批量操作的所有权校验时

## 职责

- Post-Exploit repos 只暴露 exact-scope compound writer；command/app 层不发 scope SQL。每个 evidence ID 必须属于同 operation、冻结 project path 与 organization-at-time。
- CandidateAttempt→Foothold 的 trusted source loader 只把算法已知的 `sha256:<64hex>` 规范化成 00008 Post-Exploit spine 固定的 bare `64hex`；00018 的 DB authority trigger 仍按 exact operation/snapshot/org/verified Attempt 联结并只接受同一 digest，caller/model 不能自报或替换目标哈希。

owns 全部表的结构化访问。每个表一个子模块（如 `findings.rs` / `targets.rs` / `memories.rs`），方法是 **scoped CRUD**：写/读都带 owner/project scope 校验（I2 IDOR）。`scoped.rs` 是 scope 校验基座，`audit/` 是审计相关 repo 子区。

## 注意事项 / 坑

- **Reporting repos（C9）**：`reports` / `report_revisions` / `report_sections` / `report_claims` / `report_claim_citations` / `report_source_manifest` / `report_artifact_blobs` / `report_revision_artifacts` 管理 retained history。`report_source_manifest` parser 支持 typed `stage_handoff` 与 `cleanup_blocked_decision` source；`store_read_model` 先 manifest 再 sections→claims→citations，citation 必须命中同 revision manifest source+version+hash。validation terminal 后 manifest/section/claim/citation 已是 retained immutable truth；child I/U/D 以 parent `FOR UPDATE` 与 draft→validated 串行化。validated+unpublished revision 本体的 attestation/source/metadata 完整冻结，只有 exact final transition fields 可变；final→superseded 除 publication status 与 trigger-owned version 外也不得夹带修改。`finalize_revision_with_artifacts_and_outbox` 拒绝空 artifact set，只接 server-owned current source snapshot，exact compare 后 attach content-addressed blob、CAS publication并追加 exact final outbox；00011 的 deferred authority constraint 在 commit 再核对 current revision、active local principal、artifact ref 与同版本 `ReportRevisionFinalized.v1`，因此裸 SQL final 不成立。blob reuse 使用 `ON CONFLICT DO NOTHING` 后读取并 exact identity compare，不对已引用 blob 做 no-op UPDATE。`organization_deletion_jobs::cleanup_closeout_gate_on` 是 Cleanup-owned transaction-bound只读 seam，供 Reporting build/Gate/finalize 在各自同一 PostgreSQL snapshot 内重验 closeout，不能在 Reporting 复制状态 SQL。

- `tool_calls::scoping_actions_for_session` 必须返回当前 operation Scoping 窗口内**全部** completed `scope_review`（稳定升序），不能只取 latest：第一次人工编辑/拒绝后再弹一次确认旧快照，不得把前一次决定洗掉。上层对非空 trusted snapshot 只接受 exactly one persisted review。Red-team subsidiary choice/proposal/unit review 还必须绑定调用方传入的 trusted root org：明确 parent-only choice 可直接完成该分支；纳入分支只接受同 org 成功 proposal 后的 non-skipped、可解析 unit review，不能用 finished error/skip 或乱序生命周期冒充人审。新 choice 严格验结构化 context UUID；legacy fallback 必须在 prompt 中精确出现当前 root 全名。
- Runtime-memory 新 operation 必须走 `runtime_memory_tx::create_runtime_operation`；它先在独立 best-effort transaction reconcile attack rollout，再在创建 transaction 读取两份 rollout `FOR SHARE` 并创建指定 UUID 的 task + operation + initial stage execution。禁止恢复成先 `tasks::create`、后 best-effort `operation_state::insert`。V2 CLI 还要把已经过 trusted flags/51% threshold 解析的完整 root/descendant set 一并传入，使 `CliFlags` decision 与唯一 sealed snapshot 同事务落库；后续不得重读 mutable org tree 或按 org 再开 child operation。`project_scopes` 的 canonical path 只是 provenance，授权主键始终是 DB 分配的 `project_scope_id`。
- Runtime Unit/Worker 只能走 `runtime_memory_tx` compound API：scope snapshot 派生 seed、Unit CAS + Worker lease + provider-safe message chain 预绑定、checkpoint/heartbeat/active-tool/terminal update 都先锁 operation 并按 frozen contract 决定 V2-only 或同事务 legacy mirror。production resume 必须先验证/解码一个完整 source，再用同一 source token 原子 claim exact task；后续 graph、worker、checkpoint、bound-chain 读取必须全程携带该 token。`DualWriteV2Preferred` 读取只能整条 V2 或整条 legacy fallback；任何 commit/mirror 失败必须回滚两源。
- Stage Team claim 的返回值必须携带锁后重读的当前 `StageRunUnit`；runtime 用该 Unit 的 status/row_version 刷新本地状态后才能继续 CAS/final seal。只返回 Worker/WorkItem、让 caller 沿用 claim 前 Unit 会在合法状态推进后制造 stale-CAS BLOCK。
- AttackCandidate relational synthesis 在 runtime contract 可写 V2 且 frozen attack contract `writes_v2()` 时启用；只有 operation-frozen runtime 与 attack contract 都为 `v2_only` 才可 claim verifier。`operation_state::insert` 与 `runtime_memory_tx::create_runtime_operation` 在同一短事务共享锁 rollout singleton并冻结 attack contract；现有 operation 永不重读 deployment default。Review 不接 actor id，而是在事务内读取 active local `operator_principals`。Claim 固定锁序并让 P1 WorkerRun 与 `global:exploit` lane 共用一个 lease token；heartbeat/release/verified terminalization 都是 compound transaction。
- Shadow sample 是 deployment evidence：DB 在 INSERT 内一次性关闭 attestation，不存在 caller 可占用的 pending/conclusion transition；mirror identity/content 与 comparison/source/hash/chronology 均 immutable，禁止直接 DELETE。promotion 分母来自 DB-owned Candidate admission sequence，不来自 shadow inner join；任何缺失 sample、非 terminal Wave 或 late sample 都不能逃出 cutoff。历史 mismatch 会持续阻止对应 contract promotion，不能靠逐样本清理洗掉。
- review 关闭只在短事务内把 barrier 写成 `resume_pending`；agent resume 必须在事务提交后独立 CAS `dispatching -> resumed`。同步启动失败回 `resume_pending` 并写 `last_error`；startup reaper 只重置超时 `dispatching`，绝不重开已写 approval/rejection 的 Candidate decision。
- Memory outbox 的 dedupe/staleness 必须包含 `project_scope_id`，跨客户同名 stream 不得互相冲突或判 stale；duplicate key 只有 event id、payload、source、scope、operation 与时间完全一致才算 exact replay。delivery dependency 两列必须 both-or-none，`blocked_dependency` 必须指向前驱；过期 lease 不可 terminalize。C2 production adapter/supervisor 已接入；P1 四信息阶段 final-seal 与 P2 CandidateAttempt terminalizer 都在各自原 compound transaction 内调用 typed outbox seam，任一 event/delivery 失败会回滚整个 canonical transition，且 Assertion 只由异步 deterministic promoter 产生，禁止 producer 直接写或事后补写；repo 内禁止外部 embedding/provider 请求。
- ContextPack 查询的安全顺序是 scope/ownership → classification/validity → rank；禁止先做向量相似度再用应用层过滤越权结果。Prepared action event payload 不得包含 raw plan、affected-resource snapshot、cleanup strategy 或 secret。

  guarded child IP 在 supplemental wave 形成 exact origin 后才进 Web/Enumeration 分母。

- `surface_identity_backfill.rs`（identity backfill）里 `network_endpoints` 必须以 IP:port 为主键，所以端口来源分两类：**IP target 的 `ports`** 与**显式 IP 的 target_asset** → confirmed 端点（`backfill:targets.ports` / `backfill:target_assets`）；**域名/URL target 的 `ports`** 与**被动 service target_asset（`value="<port>/<proto>"` 无 IP）** → 用该 target 的 `real_ip` 补 IP 落成 **inferred** 端点（`backfill:targets.ports.real_ip` / `backfill:target_assets.real_ip`，confidence 0.6、`last_confirmed=false`）；`real_ip` 为空则跳过（不凭空造 IP）。这样 intel 被动发现的 host:port/service 也能进 identity 层，而不是只停在 legacy target_assets。
- `js_analysis::insert` 按 `(target_id, filename)` 幂等更新最新行：`browser_collect_js_api` 的 placeholder 可先落库，`js_extract_apis` 后续原地升级为完整分析；已存在完整静态分析时，新的 collector placeholder 不能把它降级覆盖。`js_analysis::list_by_target` 返回每个 filename 的最新行，避免历史重复行把前端 JS 数量和 ENUM-JS 口径放大。
- `stage_asset_waves` 是 additive schema：wave items 固定 `target_id/value/type/source` 成员关系，gate 仍从业务表/ledger 读事实；新发现 target 不会进入当前 batch denominator，也不会在单个 org PASS 后被自动递归重跑。所有当前 org wave PASS 后，runtime 调 `create_next_or_seal_completion`：同一短事务先串行化 wave closer，并以 `targets SHARE` 锁等待已在途 writer，再读取所有未分配 in-scope backlog；有候选就创建 supplemental wave，无候选才写 `org_stage_completions` 水位。这样空 SELECT 与 pass token 之间没有可丢资产窗口；屏障提交后的 target 属于后续 operation/stage 生命周期。若 runtime 因 fresh legacy completion 没带 request-local parent，但该 operation 已有历史 wave，repo 必须在锁内取 latest wave 作为 parent；不能把 backlog 建成 parentless “首波”后被 legacy resume 规则跳过。下一次 `stage_run` 只消费 supplemental items；因此首波 limit 截断的旧资产不会永久遗漏，运行中新资产也会在后续波次出现。legacy running wave 只有在没有 parent 且全部 item 早于 fresh pass 时可补 complete；有 parent 的 supplemental wave 必须跑，不能被第一轮 pass ledger 短路。
- Runtime-memory post-Scoping PASS 只能走 `runtime_memory_tx::finalize_unit_pass`：事务按 exact operation/execution/unit/worker/submission/snapshot/lease 锁验证 deterministic Gate hash、scope hash、closed canonical catalog 和 operation-owned evidence，再共同写 Worker PASS、Unit PASS、bounded immutable `stage_handoffs`、`org_stage_completions` 与 runtime dual-write legacy mirror。Candidate dual contract 还在同一 transaction 接受 V2 decisions 并写独立 whole-record legacy semantic mirror；任一 mirror/selector-attestation 失败都回滚 final seal。四信息阶段还在该事务内写 deterministic immutable `StageEpisode` 与 `StageEpisodeClosed.v1` catalog deliveries；event/outbox 失败会把前述状态全部回滚，response-loss exact replay 仍只保留一份 episode/event/delivery DAG。普通 worker/unit CAS 会拒绝 PASS。response-loss 先对 persisted seal 做 exact shape/identity 比对（漂移稳定返回 `final_seal_replay_mismatch`），再重算 Gate/stage contract并重新 resolve canonical DB material；同一 submission/decision/payload/fence 才返回原 handoff（`replayed=true`）。Organization/Target 是锁定的 current identity，可早于 stage；producer facts仍受 Unit start freshness floor。
- Candidate final seal 的 canonical catalog 新增 `AttackCandidateWorkItem`，但只投影 frozen manifest 的不可变字段（target snapshot、identity hash、work-item key、seed technique/observation hash、manifest attestation、observation/support evidence）；decision_kind/candidate_id/decided_at/row_version 不进 content hash，因此同事务 acceptance 更新后重新 resolve 的 `content_sha256` 必须不变。该 stale-time exemption 只有 `attack_candidate` 且 canonical work-item ids 与 exact `CandidateAcceptance.expected_work_item_ids` 相等后可达。旧 predecessor evidence 只有同时属于 exact final-sealed `vuln_triage` entry handoff 和 frozen manifest evidence links 才允许；same-owner 但 unlinked、foreign、invalidated 或 hash/count 漂移一律回滚。
- `runtime_memory_tx::close_wave_gate_pass` 是 V2 wave PASS 的唯一原子 close：锁定 operation/unit/worker/wave/targets 后，要么完成 parent wave、创建一个稳定 hash 的 child wave并同事务落 `WaitingBackground` checkpoint/watermark，要么完成 terminal wave并调用内部 final seal。两条分支均不得提前写 completion；失败注入必须证明 wave、worker、unit、handoff、completion 全部 rollback。
- wave item 的 DB 主身份是 immutable membership `target_id`，`asset_value/type/source` 是创建 wave 时的 target snapshot；bridge 的 `StageAssetWaveView` 同时透传对齐的 ids/values。`current_running` 读 items 后必须用同一稳定算法重算 `asset_hash`：FK cascade 删除全部或部分 items 都会产生 empty/hash mismatch 并直接 Err，不能把损坏 wave 当 NoWave。下游 canonical-origin read model 按 target id 判成员并让 current-wave owner 优先共享-origin dedupe；submit preview 的窄 bridge 仍按 `(operation_id, organization_id, stage_kind)` scoped repo，不能信模型传入 membership。
