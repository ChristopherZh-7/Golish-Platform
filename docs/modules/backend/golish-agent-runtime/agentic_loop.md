## 注意事项 / 坑

- Stage Team child 的模型输出只有在 `complete_stage_worker` 权威事务通过后才是 immutable output。若该事务以 `final_seal_evidence_unknown_or_duplicate` 或 `final_seal_evidence_stale_or_foreign` 拒绝模型提供的 `evidence_ids`，`stage_run_call.rs` 必须先释放 Worker mutation lock，再把当前 attempt 标为 `STAGE_TEAM_WORKER_OUTPUT_EVIDENCE_INVALID` 并按稳定 WorkItem 的冻结预算重新入队；无效 manifest 不落库。child objective 要求只复制 `list_recent_evidence.evidence_id`，禁止把 generic `id` 或 audit/action/tool-call id 当证据。stale version、lease/fence、storage 与 output-hash mismatch 仍是系统错误，不得被该窄重试吞掉。
- `mod.rs` 是**薄表面**，逻辑在 `turn::*`——改 loop 行为去 turn，别把实现堆回 mod.rs。
- 透传宽 context（crate 级 `allow(too_many_arguments)`）是有意为之。
- `tool_execution/direct/mod.rs` 是 harness evidence 入账后的补充写点：recon passive 工具无论成功或失败都要写本轮 evidence/source attempt；成功时写 provider/RDAP typed terminal，失败时写 `error`（只证明尝试过，不能关 coverage），WHOIS 的 found/empty/error/blocked 不能被统一 success 文案覆盖。Scoping 尚无 frozen `harness_org_id` 时只有 `recon_discover_subsidiaries` 可请求 pre-freeze 组织绑定，而且必须把 exact operation/stage/requested root 交给 DB 重验 latest same-root human choice；模型 UUID 本身不是授权，其他 stage/tool 缺 org 继续 fail closed。授权后的 organization id 必须贯穿 evidence、technique outcome、source query 和 expansion lead，落库成功显式返回 `outcome_persisted=true`；provider completed 且 `promoted_children=0` 是 evidence-backed checked-empty，不是 retryable persistence failure。`recon_map_assets` 成功后还会触发 app bridge 标记已解析但无 DNS answers 的 in-scope domain 为 `GOLISH-INTEL-DNS empty`。target_intel duplicate guard 同时审查 generic action 与 `action:GOLISH-INTEL-*` 精确行；所有 relevant source rows 都是 found/empty/checked_empty/blocked，且对应 DNS technique outcome 不含 error/partial/running 时，才返回 `skipped_duplicate=true`。任何 retryable source/DNS outcome 都必须继续放行工具重试，与 stage spec 的 `error_is_terminal=false` 保持一致。
- `tool_execution/direct/mod.rs` 的 `run_pty_cmd` / `pentest_run` evidence 入账会派生通用 coverage facts（passive intel + EAS），并把 stdout+stderr 一起传给 outcome 判定；EAS / Enumeration wrapper 可通过 result 的 `wrapped_tool_name` / `wrapped_args` 复用这条 legacy output-store 路径。两个 Vuln Nuclei wrapper 不走该通用解析：它们 foreground 完成 exact-origin/template 校验并 evidence-first 自落 `technique_outcomes`，结果显式关闭 generic structured storage/evidence，避免重复或越级写入。EAS 里 `nmap -sn` 的 DNS failure 只在 stderr 出现，不能只看 stdout。
- `guardrail_block_reason` 不得对 `submit_stage_deliverable` 的 evidence/claim 文本套 SSRF 或 dangerous-shell 字符串阻断：submit 只做确定性校验和 DB/control-plane 写入，不会 dereference subject；合法内网/loopback Red Team 目标必须能被记录。网络执行工具仍保留 guardrail，豁免不扩散到 probe/shell。
- enumeration 四轴（GOLISH-ENUM-JS/DIR/PARAM/JSAPI）的 evidence + technique outcome 现全部由 `golish-pentest-app/src/pentest_bridge` 工具自身通过 `append_bridge_evidence` 写入（design 2026-07-03）：`browser_collect_js_api` 落 JS + JSAPI、`js_extract_apis` 落 JSAPI + PARAM、`route_probe_paths` 落 DIR。这些工具在主 agent direct 路径和 enumerator 子 agent 路径都自负落账，因此旧的「只在主 agent direct 路径跑」的 `record_enumeration_bridge_evidence` runtime hook（及其 `enumeration_evidence_projections` 等 helper）已删除——子 agent 抓到 0 JS 时也能落 `GOLISH-ENUM-JS checked_empty`（I8），不再因为 hook 缺席而永远 `not_attempted`。bridge 工具自己的 `PentestAudit` 行只是 action timeline，不能当可引用 evidence。
- `sub_agent_call.rs` 会把同一套 recon passive evidence/source_query 记录逻辑作为 `SubAgentToolResultHook` 注入给 stage-run 子 agent，避免主 agent 和子 agent 工具路径落账口径漂移。`stage_run` per-org request id 形如 `...::org::<uuid>`；子 agent 的 evidence/source_query 写入必须优先使用该 org id，而不是继承父级 root org。
- `sub_agent_call.rs` 会把 `submit_stage_deliverable needs_fix` 先交给 `stage_refiner` 生成 `RepairDirective`，再把 directive + 兼容的 `SubmitRepairMode` 写入 `operation_state.state_blob.agent_run`（同 `agent_path`）：纯 evidence/id 场景恢复为 evidence-ref repair-only，`running_background_jobs` 场景恢复为 wait-only，coverage 缺口恢复为 targeted gap-closure；下一次 resume 该 sub-agent 时通过 `initial_submit_repair_mode` 注入 executor，并发一条 SubAgentTextDelta 说明正在恢复修复，不从头扫描。
- `sub_agent_call.rs` 还会把 `stage_run` per-org request id 解析成 `active_org_id_override` 注入子 agent；普通 registry 工具如 `manage_targets` / `manage_organizations` 会收到内部隐藏 org arg，所以 `action:"list"` 只能看该 org 子树，不能靠模型自己过滤 698 个全局资产。
- `stage_run_call.rs` 在 `harness_org_id` 已绑定时必须把 DB 中的 root organization subtree 当作 fan-out 权威集合：模型传入的 `orgs` 只是 ownership/name hint，续跑/修复轮如果少传子公司，runtime 要自动补回；如果传了 subtree 外 org，则记录并丢弃，避免串到 sibling/test engagement。
- V2-writing contract 的 `stage_run_call.rs` 不再读取 mutable subtree/model org 作为执行轴：先用 frozen scope `seed_stage_runtime` 得到完整 Unit/Worker，再 exact claim+prebound chain；Passed Unit 直接 skip，GateBlocked/expired-no-active-tool 恢复同 worker。active-tool expiry默认fail closed为recovery-required；DB closed policy只允许中断的`enum_crawl_same_origin_urls`与四个EAS coverage wrapper封存旧tool后重排同一worker/chain，runtime识别server checkpoint marker并把“先`stage_worklist_status`、再`stage_worklist_next(prefer=[pending,error,partial])`、只补当前缺口、不得重放旧args”追加为本Turn host指令。每个 worker 自持 `WorkerLeaseSupervisor`，provider 前必须已 commit chain bind；普通非-stage sub-agent 保留 legacy `chain_create`。组织级 request id 只承载 Team progress；Company Controller 与它动态派发的 sibling SubAgent 必须各自派生 WorkerRun 级 UI parent id，避免并发 reasoning/tool timeline 互相污染。动态 child 的 durable `stage_worker_runs.parent_request_id` 可以共同指向派发工具 id，但执行时不得直接把这个 shared id 用作 SubAgent identity：必须无条件派生 `${dispatch_tool_request_id}::worker:<worker_run_id>`（缺 durable parent 才从 Team parent 派生），确保每个 child 拥有独立 transcript 目录、事件链和可点击详情卡。
- Target Intel / EAS / Enumeration / Vuln 不再拥有 generic per-org specialist fallback。缺少 frozen runtime-memory policy、contract 不是 `v2_only`、或 Team 路由没有在 generic loop 前接管时，`stage_run_call.rs` 分别返回 typed `STAGE_TEAM_POLICY_REQUIRED` / `STAGE_TEAM_V2_RERUN_REQUIRED` / `STAGE_TEAM_ROUTE_INVARIANT`；历史 operation 只能重开 V2 run，不能被改写成假 Team。已 final-sealed 的同 operation/stage 会先从 trusted subtree 与 fresh aggregate completion 重算 pass token，并以 `provider_dispatched=false` 幂等返回，禁止再次 seed Team 或调用模型。
- trusted resume source 由 `AgentBridge` 注入 `AgenticLoopContext`；`stage_run_call.rs` 将其写入 `LoadWorkerCheckpoint.selected_source`，并映射到 `BoundWorkerChainContext.runtime_memory_source`。恢复请求一旦选择 V2 或 LegacyFallback，checkpoint/chain 路径都不得按 worker 再查 rollout 或切换来源；missing、cross-identity、decode/fence drift 继续 fail closed。
- V2 specialist 工具必须先写 durable `tool_calls` row，再 `begin_worker_tool`；结果回灌/后处理前必须 `finish_worker_tool` 成功。heartbeat/begin/finish/checkpoint 共享 mutation lock 和 checkpoint-version witness；lease loss 会阻止下一工具并拒绝 stale landing。accepted submission 从当前 `ToolExecutionResult.value.response` 的 durable id reload，shared last-deliverable sink 仅供 legacy。
- `stage_team_dispatch_workers` 在 canonical subject 规范化后、任何 durable write 前，以 normalized role/kind/objective/sorted subjects 拒绝同 batch 的 exact assignment overlap；不同 `dedupe_key` 不能把同一 whole-company工作伪装成两个并发 Worker。该 identity 只做 batch-local 重复检测，scope authority仍由 DB frozen owner/scope重验。
- `RuntimeWorkerToolLifecycle::begin` 只有收到 typed `RuntimeMemoryError::LeaseLost` 才污染本地 bound lease；`Storage`/transient begin failure发生在工具 dispatch 前，generic tool row落 failed后由既有 child failure landing结束当前 attempt并重排稳定 WorkItem。finish failure仍按 outcome-unknown策略停止本地 Worker，不因本规则自动重放工具。
- Company Controller child drain 不再构造固定 batch 或等待整批 `join_all`。它用 `FuturesUnordered` 在既有 `max_workers_active - 1` child cap内滚动补位：任一 child完成就重新 claim queued/retry-scheduled WorkItem，即使慢 sibling仍在运行。claim future也必须持久保存、严格最多一个，并与child completion通过biased `tokio::select!`同时poll；不得先同步await claim，否则等待`operation_state`行锁的refill会阻止持锁completion提交。repository暂时返回 `None` 时暂停claim，下一项child完成后再允许重试，不能空转。parked Controller重启续跑不能只用已有WorkerRun推导可运行性：`required_work_items > terminal_required_work_items`本身就要求进入drain，以领取尚无WorkerRun的queued WorkItem；真正claim返回`None`后才可报告不可领取。单个 execution error只记录第一项并继续排空，其错误在无可领取工作后才向上层传播；claim/storage error或取消停止补领，但已启动child和已产生worker的pending claim必须完成既有落账边界。company cap、global provider semaphore、DB worker fence与真正未收敛的 lease/recovery barrier均保持不变。
- V2 per-org Gate PASS 只表示“可申请封口”，不直接计入 stage PASS。`stage_run_call.rs` 必须按 stage 构造 server-owned seal material：`target_intel` / `external_attack_surface` / `enumeration` / `vuln_triage` 从 exact operation/org/wave coverage snapshot 聚合 terminal cells；`attack_candidate` 从 frozen manifest + server-classified `CandidateAcceptance` 构造 work-item refs、typed terminal decisions、decision evidence 与 `candidate_manifest_v1` watermark。Verification 走 Candidate compound claim + opaque verifier scheduler；模型调用 `submit_candidate_attempt` 时只写 immutable TerminalIntent，不能直接结束 Attempt/Worker/lane。runtime 必须先确认 action journal 已 terminal、active tool 已清空，再持久化 exact chain/checkpoint barrier；server terminalizer 只消费 barrier-ready intent，并在单一短事务写 terminal Attempt/Candidate、可选 Finding+lineage、FactDelta/outbox，再释放 WorkerRun/global lane。action 已完成但尚未提交时，只能在同一 Attempt/Worker/chain 进入 submit-only continuation，runtime tool boundary必须拒绝再次执行 action。每次 terminalizer commit 后只发 immutable ids/status/count/replay 的 `CandidateAttemptTerminalized` trace；任一步失败保持 fail closed，绝不回退 legacy Finding writer或重放未知外部 action。
- Vuln final seal 在任何 256-key catalog bounding 前，先把 authoritative terminal coverage 与 exact operation 的完整 materialized outcome tuple set 做双向全等校验。Gate认可但producer不直接写行的Enumeration-manifest structural N/A，必须先校验exact snapshot envelope与固定source/authority/technique/canonical origin/nonempty server note，再从同operation/org/scope的final-sealed Enumeration handoff建立lineage；旧Enumeration evidence只进入有界attestation raw，不直接跨stage引用。runtime在当前Vuln operation/org/Unit/chat/project追加facts=None的新鲜aggregate evidence，并让所有可信N/A outcome共享该id；随后才生成一个`TechniqueOutcomeSet` key，并把Finding作为独立canonical key。append/upsert/set build/DB resolve/commit任一步错误都返回`COMPANY_CONTROLLER_FINAL_SEAL_FAILED`与`company_controller_finalization_failed`，关闭当前request，禁止改写成Gate repair、producer rescan或资产排除。
- 信息阶段 final-seal snapshot 必须同时传两条身份轴：`operation_id` 选择 operation-scoped outcome run，`ctx.events.session_id` 选择真实 chat evidence。尤其 Vuln wrapper 的 audit evidence 归属 chat session，禁止把 operation UUID 冒充 session，否则 org gate PASS 后的 seal 重读会丢 evidence；缺真实 session 时 fail closed。TI/EAS/Enumeration 也统一保留该调用合同。expected techniques 非空但 terminal cells 为零时，只接受 snapshot 同时明确 `summary.total_assets=0`、`assets=[]` 且没有 asset wave；缺 summary、total 非零或空 wave 都不能冒充权威零分母。
- Candidate V2 `stage_run` 在任何 provider dispatch 前读取 `AttackV2WaveAuthorityView`。Initial 只允许 generation 0 `vuln_triage` entry并由 app seed manifest；Current 只能按 exact Wave status运行，follow-on `FactDeltaConsolidation` 读取已冻结 manifest；`TerminalNoInput` org 从 worker subset 排除，Verification 全部零输入或已被 consolidation 推进时直接返回 durable no-provider success。模型 `orgs` 仅作审计 hint，不能改变 generation、WaveUnit 或 runnable org 集合。冻结 manifest prompt 对大清单明确要求首响应使用 compact groups：exact `nuclei_template_ids` 只区分安全/元数据 template，Candidate group 一次一个 template；同一 target+technique+hypothesis 的重复 observation 必须保留一项并以 `duplicate_candidate` 关闭其余项，避免模型先复述整个 manifest 或把重复项拖到 final seal。
- Candidate verifier 为每个 runnable org循环 claim opaque Attempt；每个 Attempt无论子 agent prose success 与否都必须经 persisted exact terminalizer。claim queue 排空后 runtime 调 `close_attack_v2_verification_unit`，只有 identity匹配且 `verification_closed=true, consolidation_status=ready` 才结束该 Unit；Wave 的 accept/reject/next-generation 决定留给 orchestrator 的全局 consolidation，不在 worker loop 内执行。
- V2 wave-aware PASS 保持 Worker lease 到 compound close 提交：同一事务要么完成当前 wave、创建 exact child wave 并把 Worker/Unit 停到 `WaitingBackground`，要么完成 wave 后直接写 final seal；不得先发布 org completion。response-loss replay 只接受 exact completed parent/child/checkpoint/watermark 或 exact terminal wave，早期 completed wave 不能冒充最终封口。
- `submit_stage_deliverable` 的真实 result `status=accepted` 是两层确定性终止：sub-agent executor 把它当 barrier，主 agent `tool_dispatch` 也从完整 ToolResult JSON（允许后接 runtime note）识别并立即结束当前 harness loop。不能只记录“曾 dispatch submit”等待下一个 idle turn；`needs_fix/received` 仍继续正常修复/收口。
- `stage_run`的Company Controller operator-recovery与same-request reentry blocker是另一条closed terminal contract：ToolResult必须同时携带`runtime_control.kind=halt_current_request`、closed reason及对应的`passed=false`/retry/recovery tuple；`tool_dispatch`把它翻译为typed `ToolDispatchHaltReason`，顺序封住同批后续调用，落完整paired ToolResult后立即结束当前harness request。不得仅靠prompt要求模型停止，也不得把普通工具/model JSON当作request control；下一条独立用户请求仍由top-level request owner重置guard并从durable chain继续。
- `single_tool_call.rs` 对 `DbTracker::start_tool_call` / `finish_tool_call` 必须顺序 await：
  start row 可见后才 dispatch，finish 落库后才让 Scoping/gate 评分。否则非交互 CLI
  的 `scope_review` 会出现 finish 抢在 start 前、gate 偶发读不到批准的竞态。
- `single_tool_call.rs` 的自动 tool-result memory 入口按 server-owned `harness_stage` / `harness_operation_id` 计算 `LegacyToolMemoryContext`；任何 harness customer fact 都禁止进入 legacy `memories` 自由文本表，必须等待 canonical row + outbox Memory Fabric。
- C7 active harness 在 RuntimeSupervisor prompt 与 specialist briefing 前调用 `retrieve_scoped_context_data`：subject 必须同时具有 operation/stage execution/unit/org/stage identity，provider 再从 DB 重验 frozen ownership。返回内容经 data-only renderer 注入；identity/provider/retrieval 缺失或失败不得回退 legacy global memories/wiki。非-harness 普通 sub-agent 才保留原 legacy briefing。
- `stage_run_call.rs` 只在最终 per-org gate `PASS` 后物化终态。Target Intel/EAS的兼容路径从deliverable读取blocked/not_applicable，再重读同org/session/epoch/wave authoritative snapshot，只接受exact仍pending/error/partial的asset×technique；Target Intel的organization context row可保存WHOIS/ASN/OSINT终态但永不成为scan target。Vuln走独立的backend structural-N/A路径，完全忽略model-authored coverage并先追加fresh lineage attestation。Found与checked_empty不由模型写；repo条件upsert只插缺行或替换partial/error，不降级producer terminal truth。snapshot、lineage、evidence append或upsert失败都阻止PASS；条件upsert返回false只表示并发producer/既有terminal truth胜出，可安全继续。
- Target Intel / EAS / Enumeration / Vuln Stage Team 都是 controller-only：每个 organization Unit 初始只 seed `leader:primary`，其 role 为 `company_stage_controller`。它是该公司的唯一持续主控，负责计划、检查 DB/evidence、动态派发零个或多个 sibling SubAgent、审阅 immutable child outputs，并承担 final Gate submission。实际 executor 必须由 durable Unit 的 frozen specialist 决定：四阶段分别为 `recon` / `prober` / `enumerator` / `vuln_scanner`；不再把所有 Controller/child 硬编码成 `recon`。Target Intel 的 `intel_provider` / `intel_coverage_critic` 只是允许动态创建的 child role，不是第二层主控。绑定链的 `agent_type` 与 stage specialist 必须一致，否则 restore 会在 provider 调用前 fail closed。
- Controller 成功 park 后必须立即 drop 其 live heartbeat supervisor，再等子 Worker drain；否则被故意释放的 Controller lease 会被误报为 `runtime worker lease lost`。当前无 migration schema 只能容纳同一 Controller WorkerRun 的一条 Gate gap source，所以 scheduler 将 Controller Gate repair 冻结为 1 轮，第二轮不得触发重复 durable gap 写入。

- Controller 与 child 都保留 `recon` executor，确保继续拥有 Target Intel 阶段业务工具；只有 exact trusted leader binding 会额外给 Controller 加入普通 `update_plan` 和两个 coordination controls，child prompt 则明确禁止 `update_plan`、另建计划或协调 sibling。复杂 company Unit 的首个协调轮必须先用 `update_plan` 建 1–12 步计划；未完成时恰好一项 `in_progress`。计划状态表示 Controller 当前关注点而非工具/worker 并发度：并行执行多个工具或 worker 时必须合并为一个复合 `in_progress` step，不能给每个并行动作各标一项。每次 dispatch 前、收到 durable child outputs 后、以及 Gate BLOCK/gap 同链恢复后都要先同步计划，但 `update_plan` 是普通工具，不会 park Controller 或结束协调轮；每轮仍必须以 `stage_team_dispatch_workers` 或 `stage_team_prepare_final_submission` 交还 scheduler。
- 调用 `stage_team_prepare_final_submission` 前，Controller 必须把本轮计划步骤全部标成 `completed`（允许零项 `in_progress`）；这只表示 Controller 已准备好接受确定性 Gate，不代表 Gate PASS。request epoch 关闭后的 final turn 不再修改计划，只重读 DB/evidence 并直接 `submit_stage_deliverable`。PASS 由 durable Unit/Gate truth 呈现；若 BLOCK，下一轮同一 Controller chain 用 `update_plan` 增加或重开 exact repair step 为 `in_progress`。
- Company Controller 只有在 exact trusted `StageTeamLeaderBinding` 下才看到 `stage_team_dispatch_workers` 与 `stage_team_prepare_final_submission`。前者成功返回 `dispatch_accepted` 后，runtime 会完整 checkpoint、durably park 并释放 Controller lease，由 scheduler claim/执行本轮 child WorkItem；子项 terminal 后再 exact-resume 同一 Controller message chain。后者成功返回 `prepare_final` 后关闭当前 request epoch、冻结 child-output manifest，再把同一 Controller/chain 绑定为 final submitter。Gate BLOCK 会把 durable gap 交还给同一逻辑 Controller 继续下一轮，不会创建新的“汇总 Agent”。
- Company Controller 的 coordination turn 不能用 generic `submit_result` 绕过 trusted router barrier；该调用会返回 `STAGE_TEAM_CONTROLLER_REQUIRES_ROUTER` 并保持同一 chain 继续运行，直到 Controller 调用 `stage_team_dispatch_workers` 或 `stage_team_prepare_final_submission`。final submit turn 已解除 leader binding，仍按原有 `submit_stage_deliverable` barrier 收口。

- Company Controller scheduler 的并发权威来自 StageSpec 的 C/G/K：`max_company_units_active`（C）限制同时活跃的公司 Controller Unit，`global_provider_cap`（G）限制所有 Controller 与 child 的全局 provider 并发，`max_workers`（K）限制单公司同时活跃 WorkerRun 且包含 Controller 本身；三项并发值均必须非零，计划间不一致时 fail closed。历史 `max_dynamic_requests/max_workers_total` 仍留在冻结 plan material 以保证旧 operation exact replay，但 Controller request admission、child drain、fresh claim、retry 与 coordination loop 均不得读取它们作为 lifetime fuel；队列由 durable WorkItem/barrier 终止，单次 dispatch 仍最多 32 项。
- 动态 child 的 `found/checked_empty` 在 immutable output landing 前必须与同 operation/org/stage/session 的 authoritative coverage snapshot 对齐：stable axis 映射到 exact `GOLISH-INTEL-*` technique，所有适用 cell 均已 terminal，且 found/empty disposition 与 DB truth 一致；否则作为有界可重试 contract violation fail closed。新执行的 ordinary Stage Team child 在 tool schema 与 completion prompt 两处都被要求把 `stage_worker_output.v1` object 直接传给 `submit_result.result`，generic barrier 必须保留该 object；validator 仍兼容历史纯 object或唯一 fenced payload，但多个 fence/歧义对象继续 fail closed。总体 `found` 可以同时携带其他 provider/asset 的 `checked_empty_units`，但非空 empty 子单元必须有本 WorkItem 的 evidence；`checked_empty` 本身必须同时有非空 exact units 与 evidence。协议/authority failure 走有界 Worker retry，不得固化为第一次 business BLOCK；在 scheduler 创建下一代 WorkerRun 前，runtime 必须按该代 exact parent request identity 发 `SubAgentError`，纠正 generic executor 已发出的 completed UI 状态并暴露 failure code/detail。`no_registrable_domain` 是窄 dependency retry，其他合法 blocker保持终态。Controller 的 live claim 必须跨外层 `stage_run` 重试稳定：lease owner 只由 operation/unit/plan 组成，禁止包含每次变化的 tool-call id。
- `sub_agent_call.rs` 把 durable `SubAgentResult.chain_id` 结构化透传到 tool result；`stage_run_call.rs` 对未 PASS org 会在 `operation_state.state_blob.stage_run_workers[stage][org_id]` 保存 specialist 的精确 chain UUID。结构化 `chain_id` 是唯一权威：兼容 response tail 中的 `[sub_agent_session_id: ...]` 只可在 UUID 与结构化值完全相等时被剥离，缺失、冲突或不可信 marker 都不得被当成 resume identity。重跑同 stage/org 时必须用这个 exact id resume，不能用 `resume:"latest"` 混续别的 org。DB-backed live stage_run 不能用 sub-agent 对话完成状态兜底 PASS：如果 specialist 没留下 accepted `StageDeliverable`（例如 `submit_stage_deliverable` 返回 `needs_fix` / 后台 job 未完成），该 org 必须 BLOCK 并进入 retry/gap，而不是计为 passed。
- `sub_agent_call.rs` 会把 `SubAgentChainError` 映射成稳定 `error_code + chain_failure_kind`；typed `ProviderContextLimitExceeded` 的可选、已 checkpoint UUID 同样进入 error JSON，stage worker 因而能在 non-retryable context-limit failure 后保存 exact mapping。later `FinalizeFailed` 也保持 `finalize` typed/non-retryable，但 error JSON 的 `chain_id` 只来自独立 `checkpointed_chain_id`（上一次成功 body snapshot），不使用本次失败 update 的诊断 ID；initial update 失败没有该字段。`stage_run_call.rs` 在 gate/worklist fallback 前应用安全策略。exact restore 失败只有在旧 exact id 仍在时才可重试该 id，fresh create 失败发生在工具前可有界重试，latest/finalize 失败为 non-retryable；provider input-context 超限固定映射为 `sub_agent_provider_context_limit_exceeded` + `context_limit`，无论是否已有 resume id 都 non-retryable，避免同一请求越重试越大。finalize 失败不得因缺 marker 被误当普通 BLOCK 后重开 fresh worker。
- `stage_run_call.rs` 的 resume-skip 只复用 `stage_run_id == 当前 operation UUID` 的 fresh `org_stage_completions`，并额外要求 completion 晚于本次 `operation_state.stage_started_at`；另一个并发 operation 或旧 session 的 completion 不能把 worker 短路。non-wave per-org PASS 与 wave atomic seal 都把当前 operation UUID 写入 `stage_run_id`；pass-token 生成及 orchestrator 最终重算必须同样过滤该 UUID。兼容表被并发 operation 覆盖最多造成安全的重跑/BLOCK，不能造成误 PASS。Continuation/repair 时 runtime 会把模型少传的 org 补回 authoritative subtree；这些 auto-added 但已 current-operation fresh PASS 的 org 在初始 UI seed 中必须直接发 `passed`，不要先发 `queued` 再等 serial loop 轮到它。

- `tool_execution/direct/mod.rs` 与 `sub_agent_call.rs` 的 staged evidence writer 必须同时取得 trusted `harness_operation_id` 和 `harness_org_id`，并走 organization-bound append；缺任一字段直接 fail closed，禁止回退 `DbTracker.task_id/session_uuid` 生成 final seal 必拒的 foreign evidence。Stage Team child output 的 `fact_refs` 只接受可反序列化为 `CanonicalFactKey` 的对象，runtime 会重新 canonicalize、去重并丢弃字符串/未知引用；若丢弃后既无 typed fact 又无真实 evidence，本 attempt 返回 typed `STAGE_TEAM_WORKER_OUTPUT_INVALID` violation并走 `retry_stage_worker`，只有冻结预算耗尽才形成 terminal blocker。
- `sub_agent_call.rs` 的三条模型选择分支都把同一个 `harness_operation_id` 放进 `SubAgentExecutorContext`；sub-agent executor 再把它放进每个 registry/router 工具的 `AgentToolContext`，nested delegation 继续原值透传。漏掉任一构造分支会让主 agent 与 specialist worker 的 freshness/ownership 口径漂移。
- `sub_agent_call.rs` 的三条模型选择分支还必须把 `DbTracker::session_uuid()` 放进 `SubAgentExecutorContext.persistence_session_id`。`ctx.events.session_id` 仍是 trace/transcript 文本键，headless CLI 下形如 `stage-run-*`，不能当数据库 UUID；两者混用会让 Enumerator 正常完成一段工作后没有 `sub_agent_session_id`，从而错误触发 capacity exhaustion。
- `sub_agent_call.rs`、reflector、`stage_run_call.rs` 间接启动的 worker 必须把 `AgenticLoopContext.cancelled` 传入 `SubAgentExecutorContext`；ChatPanel Stop 置位后，main agent、stage_run per-org worker、nested sub-agent 都应共享同一个停止信号。
- `single_tool_call.rs` / `sub_agent_call.rs` 用 `ExecutionMonitor` 触发 RuntimeSupervisor：重复/停滞工具命中后调用一次 LLM，解析 JSON 为 `StrategyDirective`，再由 stage/tool policy 裁剪；`shadow` 只 trace，`soft/hard` 会把 RuntimeSupervisor directive 追加到 tool result，hard 模式会让 sub-agent executor 跳过同一批剩余工具调用。
- `HarnessTraceKind::StageRefinerDecision` 在 submit needs_fix / stage_run per-org BLOCK 时发出；`HarnessTraceKind::RuntimeSupervisorDecision` 在运行中策略监督触发时发出。Candidate terminalizer 发 `CandidateAttemptTerminalized`；Verification 全局 consolidation 由 orchestrator 发 `AttackWaveConsolidated`。若 accepted FactDelta 缺少 classifier-supported typed observation，orchestrator 必须发出可观察的 `ATTACK_FACT_DELTA_ENRICHMENT_REQUIRED` BLOCK，并保持 source Wave 未关闭；不能伪造 follow-on Candidate。上述 trace 只含 immutable lineage ids、状态/decision、聚合 counts 与 replay flag，不含 plan/lease/exploit payload；`run_tree.py` / transcript summarizer 只渲染这些安全字段。
- `tool_execution/direct/mod.rs` 对 `pentest_run` registry 结果以及带 `wrapped_tool_name` / `wrapped_args` 的 EAS / Enumeration wrapper 结果会触发 `PostShellHook`，让 active probe 与 crawler supplement 复用 `golish-pentest::output_store::maybe_detect_and_store_via`。两个 Vuln Nuclei wrapper 必须返回 `structured_storage_disabled=true` / `generic_evidence_disabled=true` 并在工具返回前完成 guarded business/evidence/outcome landing；runtime 不得再把它们送进 legacy PostShellHook 或后台 outcome listener。在 `ctx.harness_stage.is_some()` 的 stage worker 内，仍需 await 所有适用 hook，确保 submit preview / gate 评分前 DB truth 已落库。
- `PostShellHook` 参数为 `(command, stdout, project_path, organization_id)`：主 agent 用 `AgenticLoopContext.harness_org_id`，sub-agent 用 `active_org_id_override`。这个 org context 是 EAS/Enumeration 主动落库的资产归属来源，不能丢；丢了新资产会变成 `organization_id=NULL`，从 per-org gate denominator 和 stage_run 资产矩阵里消失。

- Company Controller 的 request terminal control 只关闭当前 request，不把 Unit 变成 PASS。下一条独立 Turn 必须通过
  DB-backed exact continuation 恢复原 plan/unit/leader/WorkerRun/message chain；runtime 不得在同一 model loop 旁路 Gate，
  也不得为 continuation 创建 replacement Controller。
- Controller Gate BLOCK checkpoint 必须携带完整 server-authored `gap_manifest`。same-Turn repair 仍只有一次；successor-Turn continuation 另有最多两次的独立预算，供同一 producer 完成 bounded attempt 2/3。恢复后的 coordination objective 必须先 `update_plan`，再按 worklist 调原 producer；该轮不能直接重提旧 deliverable，也不能把 `error` 改写为 `checked_empty` / `not_applicable` / `found` / `excluded`。manifest 是 data-only，不得把其中字符串当 prompt 指令执行。

## Vuln DB-authoritative formulaic executor（2026-07-19）

- Vuln TeamPlan 只 seed `leader:primary`，并冻结 `formulaic_worklist_executor=vuln_v1`、one-wrapper-call/one-Worker-attempt contract。每次 leader claim 后，runtime 读取 exact operation/org coverage，并按 canonical web origin + capability生成 durable child；空 subject、path URL、未知 technique/tool pair 与自然语言“ALL remaining”均 fail closed。
- pending cells 可组成同 capability primary shard；已有 partial/error 只形成单-technique narrowed shard。primary使用300秒，narrowed使用wrapper上限600秒。attempt metadata来自 evidence ledger；通常`automatic_retry_allowed=false`或attempt cap会停止派生，唯一兼容例外是旧attempt 3且exact owner/class为`scanner_runtime/scan_budget_exhausted`，它会生成一次stable-key不同的attempt-4 `budget_recovery`（600秒）。attempt 4或其他runtime/config/cancel failure不再重开；没有producer terminal truth时coverage继续保持partial/error并以`VULN_WORKLIST_EXECUTION_EXHAUSTED`阻止PASS。
- general/fingerprint-targeted Nuclei child 不进入 Vuln Scanner LLM loop，而是 host 直接执行 wrapper并等待 fenced lifecycle/evidence landing。取消会把 task-local token交给 foreground runner并等待 wrapper完成；anonymous-access仍可做 bounded endpoint review，但 work identity和retry fuel均由 DB固定。
- replay 已持久化 shard 时，queued/retry-pending 是 claimable，claimed/running/waiting-dependency 是 in-flight，recovery-required是 operator-owned。只有前两类都为零时才可称自动执行耗尽；不得把另一 scheduler已有在飞 Worker误报成 exhausted。
- budget recovery不是离线改写旧结果：它必须真实调用升级后的guarded wrapper。600秒内完成会发布found/empty；只有wrapper认证的foreground deadline再次耗尽并由producer evidence-first落成blocked后，Gate才可把该cell视为终态。
- legacy finalizer no-purge replacement在构建Vuln worklist前调用DB adoption，仅重放same operation/source epoch的exact terminal audit witnesses并恢复source Unit freshness；随后必须重读coverage。finalizer retry checkpoint的provider chain可为array/object，runtime只解包server-owned wrapper。structural N/A落库继续使用exact `scheme://host:port`，不按host折叠 sibling origins。
