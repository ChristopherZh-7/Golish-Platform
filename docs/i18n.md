# Internationalization (i18n)

Golish ships in **English** and **Simplified Chinese (`zh-CN`)**. The two
translation tables live in `frontend/lib/i18n/` and **must stay in sync**:

- `frontend/lib/i18n/en.json`
- `frontend/lib/i18n/zh-CN.json`

`scripts/i18n_check.mjs` enforces the contract on every PR (wired into
`just check-fe` and exposed as `pnpm check:i18n`). It will fail the build
if any of the following is true:

1. `en.json` and `zh-CN.json` have drifted (a key exists on one side but
   not the other).
2. A `t("foo.bar")` or `<Trans i18nKey="foo.bar">` reference in the
   frontend code resolves to a missing key in either table.
3. A `t("key", "中文 fallback")` literal exists — using a Chinese
   default value defeats fallback for English users when the key is
   missing.

Run it locally any time:

```bash
pnpm check:i18n
```

## How language is chosen at runtime

`frontend/lib/i18n/index.ts` initializes `i18next` with a custom detector
chain:

1. **`golish.language`** in `localStorage` — set when the user picks a
   concrete language in *Settings → Appearance → Language*.
2. **`navigator.language`** — when no preference is stored or the user
   chose "Follow system".
3. **`<html lang>`** — last resort.

Supported languages are declared via `supportedLngs: ["zh-CN", "en"]`,
and `nonExplicitSupportedLngs: true` lets `zh`, `zh-TW`, `zh-HK`, `zh-SG`
all resolve to `zh-CN` instead of falling through to English.

Changing the language updates `<html lang>` automatically and persists
through page reloads.

## Adding a new translation key

```jsonc
// en.json
{
  "settings": {
    "newToggle": "Enable new feature",
    "newToggleHint": "Turning this on will reload the dashboard."
  }
}

// zh-CN.json
{
  "settings": {
    "newToggle": "启用新功能",
    "newToggleHint": "打开此选项后会重新加载控制面板。"
  }
}
```

Then in code:

```tsx
const { t } = useTranslation();
return <p>{t("settings.newToggleHint")}</p>;
```

**Do not** pass a Chinese literal as the second argument:

```tsx
// ❌ Wrong — English users will see Chinese when the key is missing
t("settings.newToggle", "启用新功能")
```

Pass interpolation values instead:

```tsx
t("targets.imported", { count: 12 })
// en.json: "Imported {{count}} targets"
// zh-CN.json: "成功导入 {{count}} 个目标"
```

## Backend (Rust) error i18n

`backend/crates/golish/src/error.rs` defines a `GolishError::I18n` variant
that serializes as `[i18n]<dotted.code>|<json-params>`. The frontend
helper `frontend/lib/errors.ts` (`localizeBackendError`) detects this
sentinel and translates the code through the `backend.errors.*` namespace.

```rust
// Rust
return Err(GolishError::i18n(
    "java.install_failed",
    serde_json::json!({ "detail": detail }),
));
```

```ts
// frontend
try {
  await invoke("install_java");
} catch (e) {
  toast.error(localizeBackendError(e));
}
```

```jsonc
// en.json
{ "backend": { "errors": { "java": { "install_failed": "Java install failed: {{detail}}" } } } }
// zh-CN.json
{ "backend": { "errors": { "java": { "install_failed": "Java 安装失败：{{detail}}" } } } }
```

For now most Rust code paths still return `anyhow::Error` with English
messages — the IPC layer keeps backwards compatibility by stringifying
those into the same plain-string contract `String(err)` consumers
already expect. Migrate hot user-facing error paths to
`GolishError::i18n` opportunistically.

## Conventions

- **Keys**: lower-camel-case under a single dotted namespace
  (`vault.refHint`, not `Vault.RefHint`).
- **Punctuation**:
  - English: standard ASCII (`Loading...`, `Settings`, etc.).
  - Chinese: full-width punctuation (`加载中…`, `保存失败：{{error}}`).
    The Chinese colon is `：`, not ASCII `:`. Use `（…）` instead of `(…)`
    when the inner text is Chinese.
- **Interpolation**: `{{name}}` — i18next default. The same key in both
  files must accept the **same** placeholders.
- **Pluralization**: i18next's `_zero` / `_one` / `_other` suffixes are
  fine to use, but for now most strings handle counts inline
  (`Imported {{count}} targets` / `成功导入 {{count}} 个目标`).

## When *not* to translate

A handful of strings are deliberately kept in Chinese inside the Rust
codebase — `i18n_check.mjs` and the backend translation pass leave them
alone:

- **Test fixtures** that assert on UTF-8 boundaries
  (`golish-core/src/utils.rs`, `golish-context/src/token_trunc.rs`).
- **AI system-prompt examples** that teach the model to recognize
  Chinese user input (`你好`, `测试`, `扫描` examples in
  `golish-prompts/src/system_prompt/*` and
  `golish-agent-runtime/src/agentic_loop/first_iter_hooks.rs`).

Adding new test fixtures or prompt examples in Chinese is fine; just
don't sprinkle Chinese literals into user-facing error or log paths.
