# Runtime Supervisor for In-Run Strategy Control

Status: active design, first implementation slice in progress
Related: `2026-06-25-stage-aware-db-refiner.md`, `2026-06-24-runtime-monitor-and-fine-grained-resume.md`, PentAGI execution monitoring model

## Problem

The StageRefiner fixes a stage after `submit_stage_deliverable` or a deterministic gate returns `needs_fix` / `BLOCK`. That is necessary, but it is too late for a different class of failures: while the main agent or a specialist is still running, it can drift into repeated tools, broad rediscovery, wrong-stage work, or stale strategy loops.

The previous Mentor path attempted to solve this, but it was too unconstrained: it could recommend broad tools or next-stage work that conflicted with the deterministic repair lock. The right shape is closer to PentAGI's execution monitor plus adviser, but with Golish's stage contract as a hard boundary.

## Decision

Introduce a RuntimeSupervisor layer:

- `ExecutionMonitor` remains a cheap trigger: repeated underlying tool, total tool count, and later evidence-progress heuristics.
- RuntimeSupervisor runs only when the trigger fires.
- RuntimeSupervisor may call an LLM, but the output must be parsed into a structured `StrategyDirective`.
- The directive is policy-sanitized against current stage spec, visible tools, active repair lock, and broad-discovery restrictions.
- The model-visible text is generated by Golish after sanitization; raw model text is not injected directly.
- Gate remains the only PASS/BLOCK authority.
- StageRefiner remains the only post-gate repair authority.

## Flow

```text
tool result
  -> evidence / DB / transcript write paths
  -> ExecutionMonitor trigger check
  -> if no trigger: return original tool result
  -> if trigger:
       build RuntimeSupervisorContext
       call RuntimeSupervisor LLM for JSON StrategyDirective
       parse or deterministic fallback
       sanitize through stage/tool policy
       emit RuntimeSupervisorDecision trace
       inject model-visible directive only in soft/hard mode
```

## Relationship To Existing Mechanisms

| Mechanism | Timing | Authority |
|---|---|---|
| RuntimeSupervisor | during tool loop after a suspicious tool result | strategy guidance only |
| StageRefiner | after submit/gate failure | repair directive only |
| Gate | stage close | deterministic PASS/BLOCK |
| LoopDetector | before runaway execution | hard block |

## First Slice

The first implementation slice covers repeated-tool / total-tool triggers. It does not yet perform DB evidence delta analysis beyond context text. The next slice can add DB-backed "no new evidence since N calls" triggers and stage-specific supervisor skills.

## Safety Rules

- Do not inject raw LLM advice.
- Do not allow supervisor advice to override an active `RepairDirective`.
- Do not recommend tools outside the stage boundary.
- In EAS repair mode, forbid broad rediscovery (`list_in_scope_targets`, `list_attack_surface_seeds`, `manage_targets`, `manage_organizations`) and prefer exact actions.
- Trace every supervisor decision with enough summary for `run_tree.py`.
